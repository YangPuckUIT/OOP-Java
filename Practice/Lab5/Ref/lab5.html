Lab 5 - Ex1: Blood Type Inheritance & Compatibility

Hướng dẫn từng bước xây dựng chương trình OOP mô phỏng di truyền nhóm máu và kiểm tra khả năng truyền máu trong Java.

Object-Oriented Programming - Java

📋 Phần 1 – Mô tả đề bài

Mục tiêu chương trình

Xây dựng chương trình Java sử dụng lập trình hướng đối tượng (OOP) để:

  • Kiểm tra nhóm máu con có hợp lệ dựa trên nhóm máu cha mẹ.
  • Kiểm tra khả năng truyền máu giữa các đối tượng trong danh sách.
  • Quản lý danh sách người kèm nhóm máu (A+/-, B+/-, AB+/-, O+/-).

Chức năng 1 – Kiểm tra nhóm máu con

Nhập nhóm máu của cha, mẹ và con. Chương trình xác định nhóm máu con có hợp lệ theo quy luật di truyền ABO + Rh hay không.

AB+O+AB+Không hợp lệ ✗

Chức năng 2 – Kiểm tra truyền máu

Nhập danh sách người (tên + nhóm máu), chọn một người nhận → tìm tất cả người có thể truyền máu cho họ.

Nếu chọn An (A+), những người có nhóm máu A+, A-, O+, O- đều có thể truyền cho An.

🔧 Phần 3 – Hướng dẫn thực hiện Step-by-Step

1

Tạo enum RhFactor

Định nghĩa yếu tố Rh (Rhesus)

🔍 Phân tích đề

Đề bài yêu cầu mỗi nhóm máu gồm 2 phần: kiểu ABO (A, B, AB, O) và yếu tố Rh (+/-). Yếu tố Rh chỉ có đúng 2 giá trị cố định: POSITIVE và NEGATIVE. Đây là tình huống lý tưởng để dùng enum.

RhFactor.javaenum
enum RhFactor {
    POSITIVE, NEGATIVE
}
💡 Giải thích code

enum trong Java tạo ra một kiểu dữ liệu với tập giá trị hữu hạn, cố định. Ở đây RhFactor chỉ có thể là POSITIVE (tương ứng dấu +) hoặc NEGATIVE (tương ứng dấu -). Không thể tạo giá trị nào khác ngoài hai giá trị này.

❓ Lý do thiết kế

Dùng enum thay vì String hay boolean vì: (1) An toàn kiểu – trình biên dịch sẽ bắt lỗi nếu truyền sai giá trị; (2) Code rõ ràng – RhFactor.POSITIVE dễ đọc hơn true hay "+"; (3) Tránh lỗi chính tả – không thể viết sai thành "POSTIIVE" như khi dùng String.

2

Tạo lớp cơ sở BloodType

Lớp cha (base class) cho tất cả các nhóm máu

🔍 Phân tích đề

Có 4 nhóm máu ABO (A, B, AB, O) – mỗi nhóm có hành vi riêng về di truyền và truyền máu, nhưng đều chia sẻ thuộc tính Rh và các phương thức chung (toString, equals). Đây là bài toán kế thừa điển hình: tạo một lớp cha BloodType chứa phần chung, các lớp con sẽ override phần riêng.

BloodType.javaclass
public class BloodType {
    protected RhFactor rh;

    public BloodType(RhFactor rh) {
        this.rh = rh;
    }

    public RhFactor getRh() {
        return rh;
    }

    // Lớp con sẽ override để trả về "A", "B", "AB", "O"
    public String getType() {
        return "Unknown";
    }

    // Lớp con override: trả về tập nhóm máu con có thể có
    public Set<String> possibleChildren(BloodType otherParent) {
        return new HashSet<>();
    }

    // Lớp con override: kiểm tra truyền máu
    public boolean canReceiveFrom(BloodType donor) {
        return false;
    }

    public String toString() {
        return getType() + (rh == RhFactor.POSITIVE ? "+" : "-");
    }

    public boolean equals(Object o) {
        if (o instanceof BloodType) {
            BloodType bt = (BloodType) o;
            return this.toString().equals(bt.toString());
        }
        return false;
    }
}
💡 Giải thích code

protected RhFactor rh – thuộc tính Rh được đánh dấu protected để các lớp con (AType, BType…) có thể truy cập trực tiếp.

getType() – trả về "Unknown" mặc định; mỗi lớp con sẽ override trả về kiểu cụ thể ("A", "B"…).

possibleChildren() – trả về HashSet rỗng mặc định; lớp con override để cài đặt bảng di truyền.

canReceiveFrom() – trả về false mặc định; lớp con override để cài đặt quy tắc truyền máu.

toString() – gọi getType() + thêm dấu "+" hoặc "-" dựa trên Rh. Nhờ tính đa hình, khi gọi trên đối tượng AType, nó sẽ trả về "A+" hoặc "A-".

equals() – so sánh hai đối tượng BloodType bằng cách so sánh chuỗi toString().

❓ Lý do thiết kế

Lớp BloodType đóng vai trò abstraction layer: phần còn lại của chương trình (Person, BloodTypeProgram) chỉ cần làm việc với kiểu BloodType mà không cần biết cụ thể đó là A, B, AB hay O. Đây là nguyên lý Dependency Inversion – phụ thuộc vào abstraction, không phụ thuộc vào implementation. Các phương thức trả về giá trị mặc định (thay vì abstract) để code linh hoạt hơn – lớp con chỉ cần override những gì cần thay đổi.

📝 Lưu ý: Trong lab, lớp này không được khai báo abstract (dù tiêu đề ghi "Abstract Class"). Các phương thức có implementation mặc định thay vì dùng từ khóa abstract. Cách làm này vẫn đạt được hiệu quả tương tự – lớp con bắt buộc phải override để có hành vi đúng.
3

Tạo lớp con AType

Cài đặt quy luật di truyền và truyền máu cho nhóm A

🔍 Phân tích đề

Nhóm máu A cần cài đặt 2 thứ: (1) Di truyền – bảng kết hợp A với các nhóm khác cho ra những nhóm máu nào ở con; (2) Truyền máu – A chỉ nhận từ A và O, kèm quy tắc Rh.

AType.javaextends BloodType
class AType extends BloodType {
    public AType(RhFactor rh) {
        super(rh);
    }

    @Override
    public String getType() {
        return "A";
    }

    @Override
    public Set<String> possibleChildren(BloodType other) {
        Set<String> result = new HashSet<>();
        String otherType = other.getType();
        switch (otherType) {
            case "A":
                result.addAll(List.of("A", "O"));
                break;
            case "B":
                result.addAll(List.of("A", "B", "AB", "O"));
                break;
            case "AB":
                result.addAll(List.of("A", "B", "AB"));
                break;
            case "O":
                result.addAll(List.of("A", "O"));
                break;
        }
        return result;
    }

    @Override
    public boolean canReceiveFrom(BloodType donor) {
        return donor.getType().equals("A") || donor.getType().equals("O") &&
               (donor.getRh() == RhFactor.NEGATIVE || this.rh == RhFactor.POSITIVE);
    }
}
💡 Giải thích code

Constructor AType(RhFactor rh) – gọi super(rh) để truyền giá trị Rh lên lớp cha BloodType khởi tạo.

getType() – override trả về "A", xác định đây là nhóm máu A.

possibleChildren() – dùng switch trên kiểu nhóm máu của cha/mẹ còn lại để tra bảng di truyền. Ví dụ: A + B → có thể sinh ra A, B, AB, O. Dùng HashSet để tự loại bỏ giá trị trùng lặp.

canReceiveFrom() – logic 2 phần: (1) Kiểu ABO: chỉ nhận từ A hoặc O; (2) Kiểu Rh: nếu donor là Rh- thì luôn OK, hoặc nếu bản thân (this) là Rh+ thì cũng nhận được Rh+.

❓ Lý do thiết kế

Mỗi lớp con chỉ chịu trách nhiệm quy luật riêng của nhóm máu đó – đây là nguyên lý Single Responsibility. Khi cần thay đổi quy luật nhóm A, chỉ sửa file AType.java mà không ảnh hưởng đến các nhóm khác. Việc dùng switch-case giúp code dễ đọc – mỗi case tương ứng trực tiếp với một dòng trong bảng di truyền.

4

Tạo lớp con BType, ABType, OType

Áp dụng cùng pattern cho các nhóm máu còn lại

🔍 Phân tích đề

Cấu trúc giống hệt AType, chỉ khác ở nội dung bảng di truyền và quy tắc nhận máu. Đây là sức mạnh của OOP: một template chung (BloodType), mỗi lớp con chỉ cần điền dữ liệu riêng.

BType.javaextends BloodType
class BType extends BloodType {
    public BType(RhFactor rh) { super(rh); }

    @Override
    public String getType() { return "B"; }

    @Override
    public Set<String> possibleChildren(BloodType other) {
        Set<String> result = new HashSet<>();
        switch (other.getType()) {
            case "A":  result.addAll(List.of("A","B","AB","O")); break;
            case "B":  result.addAll(List.of("B","O")); break;
            case "AB": result.addAll(List.of("A","B","AB")); break;
            case "O":  result.addAll(List.of("B","O")); break;
        }
        return result;
    }

    @Override
    public boolean canReceiveFrom(BloodType donor) {
        return donor.getType().equals("B") || donor.getType().equals("O") &&
               (donor.getRh() == RhFactor.NEGATIVE || this.rh == RhFactor.POSITIVE);
    }
}
ABType.javaextends BloodType
class ABType extends BloodType {
    public ABType(RhFactor rh) { super(rh); }

    @Override
    public String getType() { return "AB"; }

    @Override
    public Set<String> possibleChildren(BloodType other) {
        Set<String> result = new HashSet<>();
        switch (other.getType()) {
            case "A":  result.addAll(List.of("A","B","AB")); break;
            case "B":  result.addAll(List.of("A","B","AB")); break;
            case "AB": result.addAll(List.of("A","B","AB")); break;
            case "O":  result.addAll(List.of("A","B")); break;
        }
        return result;
    }

    @Override
    public boolean canReceiveFrom(BloodType donor) {
        // AB là universal receiver (nhận từ tất cả kiểu ABO)
        return donor.getRh() == RhFactor.NEGATIVE || this.rh == RhFactor.POSITIVE;
    }
}
OType.javaextends BloodType
class OType extends BloodType {
    public OType(RhFactor rh) { super(rh); }

    @Override
    public String getType() { return "O"; }

    @Override
    public Set<String> possibleChildren(BloodType other) {
        Set<String> result = new HashSet<>();
        switch (other.getType()) {
            case "A":  result.addAll(List.of("A","O")); break;
            case "B":  result.addAll(List.of("B","O")); break;
            case "AB": result.addAll(List.of("A","B")); break;
            case "O":  result.addAll(List.of("O")); break;
        }
        return result;
    }

    @Override
    public boolean canReceiveFrom(BloodType donor) {
        // O chỉ nhận từ O
        return donor.getType().equals("O") &&
               (donor.getRh() == RhFactor.NEGATIVE || this.rh == RhFactor.POSITIVE);
    }
}
💡 Giải thích code

Cả 3 lớp đều tuân theo cùng một khuôn mẫu (pattern) như AType:

BType — nhận máu từ B và O. Di truyền: B+B→B,O; B+A→A,B,AB,O; B+AB→A,B,AB; B+O→B,O.

ABType — là universal receiver về ABO (nhận từ mọi nhóm), nên canReceiveFrom chỉ cần kiểm tra Rh mà không cần kiểm tra kiểu ABO. Di truyền: AB không bao giờ sinh ra O.

OType — chỉ nhận từ O (khắt khe nhất). Nhưng O là universal donor — tất cả nhóm máu đều có thể nhận từ O. Di truyền: O+O chỉ sinh ra O.

❓ Lý do thiết kế

Tách thành 4 lớp con riêng biệt thay vì dùng if-else lồng nhau trong một lớp duy nhất giúp: (1) Mở rộng dễ — nếu cần thêm nhóm máu mới, chỉ tạo thêm lớp mới; (2) Bảo trì dễ — mỗi file chỉ chứa logic của 1 nhóm máu; (3) Đa hình (Polymorphism) — code gọi bloodType.possibleChildren() không cần biết đó là A, B, AB hay O — Java tự gọi đúng phương thức.

Tạo lớp Person

Đại diện cho một người với tên và nhóm máu

🔍 Phân tích đề

Đề yêu cầu quản lý danh sách người, mỗi người có tên và nhóm máu. Cần tạo class Person để đóng gói 2 thuộc tính này, hỗ trợ hiển thị thông tin và so sánh.

Person.javaclass
class Person {
    String name;
    BloodType bloodType;

    public Person(String name, BloodType bloodType) {
        this.name = name;
        this.bloodType = bloodType;
    }

    public String getName() {
        return name;
    }

    public BloodType getBloodType() {
        return bloodType;
    }

    public String toString() {

💡 Giải thích code

BloodType bloodType — thuộc tính kiểu BloodType (lớp cha), không phải kiểu cụ thể AType hay BType. Nhờ vậy Person có thể chứa bất kỳ nhóm máu nào — đây là đa hình (Polymorphism).

toString() — khi in Person, nó tự động gọi bloodType.toString() để hiển thị dạng "An (A+)".

❓ Lý do thiết kế

Lớp Person tách biệt "ai" (tên) khỏi "nhóm máu gì" (BloodType). Đây là nguyên lý Composition — Person có một BloodType, thay vì là một BloodType. Điều này giúp mỗi lớp giữ trách nhiệm rõ ràng: Person quản lý thông tin cá nhân, BloodType quản lý logic y tế.

6

Tạo phương thức createBloodType()

Factory method chuyển chuỗi thành đối tượng BloodType

🔍 Phân tích đề

Người dùng nhập nhóm máu dạng chuỗi ("A+", "O-", "AB+"). Cần một phương thức chuyển đổi chuỗi này thành đối tượng tương ứng (AType, OType…). Đây chính là Factory Pattern.

BloodTypeProgram.java — createBloodType()static method
public static BloodType createBloodType(String fullType) {
    String type;
    RhFactor rh;

    fullType = fullType.trim().toUpperCase();

    if (fullType.endsWith("+")) {
        rh = RhFactor.POSITIVE;
        type = fullType.substring(0, fullType.length() - 1);
    } else if (fullType.endsWith("-")) {
        rh = RhFactor.NEGATIVE;
        type = fullType.substring(0, fullType.length() - 1);
    } else {
        throw new IllegalArgumentException(
            "Invalid format. Use types like A+, B-, AB+, O- etc.");
    }

    switch (type) {
        case "A":  return new AType(rh);
        case "B":  return new BType(rh);
        case "AB": return new ABType(rh);
        case "O":  return new OType(rh);
        default:
            throw new IllegalArgumentException("Unknown blood type: " + type);
    }
}
💡 Giải thích code

Bước 1: Chuẩn hóa input — trim() xóa khoảng trắng thừa, toUpperCase() chuyển thành chữ hoa để xử lý đồng nhất ("a+" → "A+").

Bước 2: Tách Rh — ký tự cuối cùng ("+" hoặc "-") xác định yếu tố Rh. Phần còn lại là kiểu ABO.

Bước 3: Tạo đối tượng — dùng switch để khởi tạo đúng lớp con. Kiểu trả về là BloodType (lớp cha), nhưng đối tượng thực tế là AType, BType… → đa hình.

Xử lý lỗi — nếu input không hợp lệ, ném IllegalArgumentException với thông báo rõ ràng.

❓ Lý do thiết kế

Đây là Factory Method Pattern: tập trung logic tạo đối tượng vào một nơi duy nhất. Phần còn lại của chương trình không cần biết có bao nhiêu lớp con hay cách khởi tạo chúng — chỉ cần gọi createBloodType("A+"). Khi thêm nhóm máu mới, chỉ cần thêm một case ở đây.

7

Tạo phương thức isValidChild()

Kiểm tra tính hợp lệ của nhóm máu con

🔍 Phân tích đề

Chức năng 1 yêu cầu kiểm tra nhóm máu con có hợp lệ không. Cần kiểm tra 2 điều kiện: (1) Kiểu ABO của con nằm trong tập có thể; (2) Nếu cả cha mẹ đều Rh-, con phải Rh-.

BloodTypeProgram.java — isValidChild()static method
public static boolean isValidChild(
        BloodType father, BloodType mother, BloodType child) {

    Set<String> possible = father.possibleChildren(mother);

    return possible.contains(child.getType()) &&
           ((father.getRh() == RhFactor.NEGATIVE
             && mother.getRh() == RhFactor.NEGATIVE)
                ? child.getRh() == RhFactor.NEGATIVE
                : true);
}
💡 Giải thích code

Dòng 1: Gọi father.possibleChildren(mother) để lấy tập nhóm máu ABO mà con có thể có.

Điều kiện 1: possible.contains(child.getType()) — kiểu ABO của con phải nằm trong tập cho phép.

Điều kiện 2 (ternary): Nếu cả cha và mẹ đều Rh- → con bắt buộc Rh-. Ngược lại (ít nhất 1 người Rh+) → con có thể Rh+ hoặc Rh-, nên trả về true.

Cả 2 điều kiện được nối bằng && — cả hai phải đúng.

❓ Lý do thiết kế

Phương thức static vì nó không thuộc về bất kỳ đối tượng nào — nó là logic chung kiểm tra mối quan hệ giữa 3 đối tượng. Dùng ternary operator giúp gộp logic Rh thành 1 biểu thức gọn, tránh viết if-else dài dòng.

Viết phương thức main()

Kết nối tất cả lại — nhập liệu, xử lý, xuất kết quả

🔍 Phân tích đề

Chương trình main cần thực hiện 3 phần tuần tự: (a) Nhập danh sách người + nhóm máu; (b) Kiểm tra nhóm máu con; (c) Tìm người có thể truyền máu cho một người chỉ định.

BloodTypeProgram.java — main()Part a: Nhập danh sách
public static void main(String[] args) {
    Scanner sc = new Scanner(System.in);
    List<Person> people = new ArrayList<>();

    // Part a: Nhập danh sách người
    System.out.print("Enter number of people: ");
    int n = sc.nextInt();
    sc.nextLine();  // Đọc bỏ ký tự xuống dòng

    for (int i = 0; i < n; i++) {
        System.out.print("Enter name: ");
        String name = sc.nextLine();
        System.out.print("Enter blood type (A+/A-/B+/AB-/...): ");
        String type = sc.nextLine();
        people.add(new Person(name, createBloodType(type)));
    }
💡 Giải thích code — Part a

sc.nextLine() sau nextInt() là bắt buộc — nextInt() chỉ đọc số, không đọc ký tự xuống dòng \n. Nếu không gọi nextLine() bổ sung, lần gọi nextLine() tiếp theo sẽ đọc chuỗi rỗng thay vì tên người.

Mỗi lần lặp: đọc tên → đọc nhóm máu → dùng createBloodType() chuyển chuỗi thành đối tượng → tạo Person → thêm vào list.

BloodTypeProgram.java — main()Part b: Kiểm tra con
    // Part b: Kiểm tra nhóm máu con
    System.out.println("\n== Check Child Validity ==");
    System.out.print("Father's blood type: ");
    BloodType father = createBloodType(sc.nextLine());
    System.out.print("Mother's blood type: ");
    BloodType mother = createBloodType(sc.nextLine());
    System.out.print("Child's blood type: ");
    BloodType child = createBloodType(sc.nextLine());

    boolean valid = isValidChild(father, mother, child);
    System.out.println("Is child blood type valid? " +
                       (valid ? "Yes" : "No"));
BloodTypeProgram.java — main()Part c: Tìm donor
    // Part c: Tìm người truyền máu phù hợp
    System.out.println("\n== Blood Donor Matching ==");
    System.out.print("Enter person name to find donors: ");
    String targetName = sc.nextLine();
    Person target = null;

    for (Person p : people) {
        if (p.getName().equalsIgnoreCase(targetName)) {
            target = p;
            break;
        }
    }

    if (target == null) {
        System.out.println("Person not found.");
    } else {
        System.out.println("Compatible donors for " + target.getName() + ":");
        for (Person donor : people) {
            if (!donor.equals(target) &&
                target.getBloodType().canReceiveFrom(donor.getBloodType())) {
                System.out.println("- " + donor);
            }
        }
    }
}
💡 Giải thích code — Part b & c

Part b: Nhập nhóm máu cha, mẹ, con → gọi isValidChild() → in "Yes" hoặc "No". Factory method createBloodType() xử lý việc chuyển chuỗi thành đối tượng.

Part c — Tìm người nhận: Duyệt danh sách people, so sánh tên (không phân biệt hoa thường) bằng equalsIgnoreCase().

Tìm donor: Với mỗi người khác trong list, gọi target.getBloodType().canReceiveFrom(donor.getBloodType()). Đây là nơi đa hình phát huy — dù getBloodType() trả về kiểu BloodType, Java tự động gọi đúng phương thức canReceiveFrom() của lớp con cụ thể (AType, BType…).

!donor.equals(target) — loại trừ chính người nhận ra khỏi danh sách donor.

❓ Lý do thiết kế

Phương thức main không chứa bất kỳ logic y tế nào — nó chỉ làm 3 việc: nhập liệu, gọi phương thức, xuất kết quả. Toàn bộ logic nghiệp vụ nằm trong các class (BloodType, Person). Đây là nguyên lý Separation of Concerns — tách phần giao diện (I/O) khỏi phần xử lý (business logic), giúp dễ thay đổi giao diện (từ console sang GUI) mà không đụng đến logic.

🏭 Phần 5 — Tổng quát các bước thực hiện một bài toán OOP bất kỳ

Quy trình dưới đây áp dụng cho đa số đề OOP: từ đọc đề đến thiết kế lớp & quan hệ, rồi main và thứ tự code. Bài nhóm máu trong tài liệu này minh họa trực tiếp các bước 2–6.

1

Đọc và phân tích đề bài

Mục tiêu
  • Hiểu bài toán yêu cầu gì.
  • Xác định dữ liệu cần quản lý.
  • Xác định hành động / chức năng cần thực hiện.
Cần trả lời các câu hỏi
1. Bài toán quản lý cái gì? → thường trở thành class.
2. Mỗi đối tượng có thông tin gì? → đó là attributes (thuộc tính).
3. Đối tượng có thể làm gì? → đó là methods (phương thức).
2

Xác định các class

Quy tắc chung: danh từ (thực thể trong đề) → thường là class.

Gom các khái niệm trùng nghĩa, tránh tạo quá nhiều lớp trùng vai trò; có thể phác nhanh tên lớp trên giấy trước khi viết code.

3

Thiết kế thuộc tính (attributes)

Mỗi class cần lưu thông tin gì? Liệt kê theo từng lớp, gắn với kiểu dữ liệu phù hợp (int, String, kiểu tham chiếu tới lớp khác…).

Nguyên tắc (encapsulation)
  • Thuộc tính thường để private — không cho truy cập trực tiếp từ bên ngoài.
  • Mục đích: đóng gói (encapsulation), ẩn dữ liệu (data hiding), kiểm soát cách đọc/ghi giá trị.
  • Chỉ public khi thật sự cần (ví dụ hằng số, API rõ ràng của thư viện).
  • Thông thường truy cập qua getter / setter (có thể thêm kiểm tra hợp lệ trong setter).
4

Thiết kế phương thức (methods)

Xác định object có thể làm gì (hành vi nghiệp vụ, không trộn với nhập/xuất console nếu có thể tách).

Các loại method phổ biến
  • Constructor: khởi tạo đối tượng (gán giá trị ban đầu cho thuộc tính).
  • Getter / Setter: đọc và ghi thuộc tính có kiểm soát.
  • Input / Output: có thể nằm ở lớp điều khiển / main; phần cốt lõi nên là method nghiệp vụ thuần (dễ test).
5

Xác định quan hệ giữa các class

Association (liên kết)
Một class biết hoặc sử dụng class khác (tham chiếu, gọi method)— mức độ gắn kết tùy bài.
Aggregation / Composition (has-a)
Một object chứa object khác. Composition: vòng đời thường gắn chặt với object cha; Aggregation: bớt phụ thuộc hơn — có thể bổ sung sau khi nắm has-a.
Inheritance (kế thừa)
Khi có quan hệ “is-a” (lớp con là một kiểu lớp cha). Dùng extends / implements cho phần chung & phần riêng.
Polymorphism (đa hình)
Nhiều đối tượng cùng kiểu tham chiếu (cha / interface) nhưng hành vi cụ thể khác nhau lúc chạy — thường đi cùng override / interface, là cơ chế hơn là một kiểu liên kết UML đơn giản như association.
6

Viết chương trình chính (main)

Tạo đối tượng → gọi method → in kết quả. main nên gọn: nhập liệu, điều phối luồng, gọi xuống các lớp đã thiết kế.

new …  →  gọi phương thức nghiệp vụ  →  hiển thị / trả kết quả
7

Thứ tự triển khai gợi ý (khi viết code)

Kiểu phụ trợ (enum, hằng, lớp tiện ích) → lớp cha / interface → lớp con (override từng quy tắc) → lớp thành phần (composition) → factory / service tĩnh → cuối cùng main nối I/O.

Cách làm này giúp biên dịch từng lớp và dễ kiểm thử từng phần.
💡 Mẹo làm bài: Khi gặp bài OOP, hãy bắt đầu bằng cách xác định: (1) Có những đối tượng nào? (2) Chúng có điểm chung gì → tạo lớp cha. (3) Chúng khác nhau ở đâu → tạo lớp con override. (4) Đối tượng nào chứa đối tượng nào → composition. Cách tiếp cận top-down này giúp bạn thiết kế hệ thống class rõ ràng trước khi viết code.
